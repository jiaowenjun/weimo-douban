# AI 查询问题排查

本页适用于已按[连接指南](README.md#生成连接配置)接入 `weimo-douban` 的 MCP 使用者。遇到错误时，先展开工具调用详情，查看**实际参数和原始错误**。助手对失败原因的文字解释可能不准确。

## 先确认最小查询可以成功

1. 调用 `list_users`，参数为 `{}`，从返回的 `items` 中取得 `uid`。
2. 调用 `search_marks`，只传下面的对象，将占位文字替换为实际 `uid`：

   ```json
   {"uid":"从 list_users 获取的实际 ID"}
   ```

3. 成功后，添加一个条件重试，例如只看电影：

   ```json
   {"uid":"从 list_users 获取的实际 ID","category":"movie"}
   ```

4. 再逐项添加日期、星级等筛选条件。若加条件后失败，保留失败的参数与错误，用 `get_stats` 传入同样的筛选条件，或换一个模型／客户端做对照，帮助区分问题范围。

这些 JSON 是工具的参数对象。`uid`、`category`、`marked_from`、`limit` 等字段都放在顶层，不要包在 `filter`、`page` 中，也不要将整个对象作为字符串传入。`search_marks`、`get_stats`、`list_facets` 的 `uid` 始终必填，本地只有一个用户也一样。

最小调用成功，只能确认这条调用路径可用。`search_marks` 的 `total` 是匹配总数，`items` 才是当前页的记录，默认最多 20 条；不能把第一页当成全部结果。读取后续页使用 `next_offset`，完整计数使用 `get_stats`。如果多参数调用仍失败，分页和筛选也可能受影响，不要据此给出完整榜单或年度统计。

## 根据错误判断下一步

| 看到的现象 | 应检查什么 |
|---|---|
| MCP 无法启动，提示数据库尚未初始化或结构不兼容 | 确认 App 已同步过数据、连接配置指向正确的数据目录，并使用配套版本 App 初始化或升级；之后重新连接 MCP |
| `missing field uid`，或输入 Schema 校验失败 | 查看失败调用自己的参数，确认 `uid` 在顶层；相邻工具调用中的 `uid` 不会自动沿用 |
| 助手声称传了参数，调用详情却显示 `{}` | 检查客户端是否发生参数解析失败；空对象可能是客户端的错误恢复结果 |
| 合法参数可以直连 MCP 查询，但某个助手反复失败 | 优先检查该客户端与模型的参数生成、流式处理、JSON 解析和校验路径；直连成功不能证明整个助手调用链正常 |
| 查询成功，但数量或内容不符合预期 | 核对 `uid`、数据目录、筛选范围、分页与同步状态；「今年看过」使用标记日期 `marked_from/to`，不是作品年份 |

App 升级或连接配置变更后，应重新连接 MCP，使客户端加载新程序和工具定义。不要仅依赖旧对话中缓存的工具说明。

## 实例：ZCode + GLM-5.3 的空参数错误

2026-11-01，在 ZCode + GLM-5.3 的一次会话中观察到下列现象。日志中的 MCP 客户端版本为 `0.17.1`；这是当次环境的记录，不是所有 ZCode 版本或 GLM 模型的兼容性结论。

| 当次调用 | 观察结果 |
|---|---|
| `list_users({})` | 成功 |
| `get_stats` / `search_marks` 只传 `uid` | 成功 |
| `search_marks` 多参数，第一轮 5 次 | 均解析失败；日志中的原始参数字符串长度为 62、63 或 72 |
| `search_marks` 多参数，后续一次 | 解析失败；日志记录长度 98 |
| `search_marks` / `get_stats` 两参数，各一次 | 均解析失败；日志记录长度均为 35 |
| 绕过模型，使用合法 JSON 直接调用安装版 MCP | 多参数筛选成功 |

失败调用在界面上显示 `{}` 和 `Tool input failed inputSchema validation`。客户端日志提供了更早的错误：

```text
event: model.tool_input.normalize_failed
parseErrorType: SyntaxError
recovery: empty_object
source: streamText
```

结合当时客户端的解析逻辑，可以确认：**收到非空参数字符串 → JSON 解析失败 → 客户端替换为 `{}` → 校验发现缺少 `uid` → 请求未进入 MCP 查询处理。** 模型收到的工具定义保留了顶层参数和必填 `uid`。

因此，「模型忘了传参数」并不能解释本例。但当时日志没有保留解析前的字符串，也无法断言「ZCode 把合法 JSON 弄坏了」。GLM 输出非法 JSON、服务商接口或客户端流式拼接异常等原因仍需原始数据验证。「单参数成功、两参数失败」只是本次样本的规律；长度阈值、逗号或分块问题均未证实。

## 如何提供有用的反馈

记录客户端和模型版本、App 版本、发生时间、工具名称、成功与失败的实际参数、原始错误。说明是否只在某个模型中发生，以及重新连接后是否仍能复现。

ZCode 在本次环境中的日志位于 `~/.zcode/cli/log/zcode-YYYY-MM-DD.jsonl`。可搜索 `model.tool_input.normalize_failed` 和对应工具名称，保留附近相关条目；具体位置和字段可能随客户端版本变化。`inputLength` 是客户端解析前的字符串长度，应以日志为准，不能用助手估算的 JSON 长度代替。

若日志只有 `SyntaxError` 和 `recovery: empty_object`，需要客户端维护者进一步提供或启用诊断：记录解析前原始参数、完整语法错误及相关流式片段，并将解析错误反馈给模型，避免回填 `{}` 后只留下误导性的缺参错误。分享诊断时只提供相关片段，隐去账号标识、路径、凭据和私人短评。

## 不要用丢弃筛选条件来绕过错误

将 `uid` 改为可选并自动选择唯一用户，无法恢复已丢失的日期、类别等条件；反而可能让一次“今年电影”查询在参数被清空后悄悄变成“全部记录”。

将全部筛选条件塞入一个 JSON 字符串字段也不是已验证的解决办法，它增加了转义层次并削弱参数类型约束。当前工具没有提供这种入口。

临时可使用已验证成功的最小调用检查连接，或换模型／客户端做对照。只有原本需要的筛选条件完整传入并查询成功后，才能据此生成对应清单或统计结论。

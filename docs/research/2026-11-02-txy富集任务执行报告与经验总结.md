口径约定：

- **失败次数**是请求事件数，**失败条目数**按 `(category, subject_id)` 去重，两者不可混用。
- **已恢复**要求同一个条目在失败之后出现成功日志，且数据库有对应 `source=rexxar, status=ok` 的缓存行。
- **终态失败**指 job 进入 `error` 或 `not_found`；仍在等待重试、或被清空的 job 不属于这两个状态。
- **完成度**以 records 去重条目为分母、对应 subjects 为分子，不能以清理后剩余 job 的成功率替代。
- 时间以 journal 的事件时间戳转换为 UTC+8。日志消息内的 `Z` 时间是 UTC，不能直接当北京时间使用。

## 5. 失败、恢复与调度机制

### 5.1 160 次失败的实际去向

| 指标 | 结果 |
|---|---:|
| 失败请求事件 | 160，全部 movie / HTTP 400 |
| 涉及不同条目 | 152 |
| `attempt=1` / `attempt=2` | 152 / 8 |
| `attempt>=3` | 0，最大尝试次数配置为 5（含首次） |
| 后来成功的失败条目 | **49**，对应 **57** 次失败事件 |
| 截至中断仍未富集的失败条目 | **103**，对应 **103** 次失败事件 |
| 终态 error / not_found、intro 降级、熔断 | 本次日志与清空后数据库未见 |

49 个已恢复条目来自 10-30 至 10-31 的失败批次。11-01 至 11-02 的 103 个失败条目，在完整事件匹配中没有后续成功记录，数据库也没有对应 subjects 或 job 行；它们包含在剩余 1983 条缺口中。

**“没有 attempt=3”只能说明没有记录到第三次失败，不能证明前两次失败都已自愈。** 相同条目可能尚未再次被调度。

### 5.2 重试不会保证成为冷却后的下一条请求

实现链路见 [subject.rs](../../backend/src/server/subject.rs) 的 `handle_job_error`、`defer_category_jobs`、`pick_due_job`，以及 [state.rs](../../backend/src/server/state.rs) 的类别间隔函数：

1. `Blocked` 被视为可重试错误，记录 `attempts + 1`。
2. 类别间隔乘 3，最高 90 秒；成功后乘 0.9，逐步收缩到配置下限。
3. 同类别非强制 job 推迟到类别冷却截止时间，默认 300 秒加 0–30 秒抖动。
4. 当前失败 job 同时采用指数退避（20 / 60 / 180 / 540 秒，加抖动），实际重试时刻取退避和类别冷却两者较晚值。
5. 到期 job 按 `priority ASC, updated_ms ASC, rowid ASC` 选取。失败会刷新自身 `updated_ms`，同优先级、较早入队且尚未尝试的条目因而可能先执行。

因此，冷却结束后先成功的往往是另一个条目。现有设计能维持端点继续工作，也能将单条失败留在队列里等待，但**端点恢复和失败条目完成是两个不同事件**。本次后期大队列中，103 个失败条目尚未等到完成就被清空。

达到第 5 次失败时，代码才尝试 intro 兜底；没有可用 records 行时才保留 `error`。本次未走到这条路径。成功路径会清空 `attempts/last_error`，因此 journal 是本次逐条恢复对账的必要历史证据。

## 6. 限流特征与吞吐

### 6.1 可以确认的现象

- **类别差异明显。** book 约 4 秒/条；music 的 1961 条在约 127 分 48 秒内完成，平均约 3.91 秒/条，零 music 失败。movie 在更慢节奏下仍持续收到 400，符合此前记录的 movie 端点限流特征。
- **movie 出现反复收缩、失败、冷却、恢复的循环。** 例如 11-02 09:35:17 至 09:36:30，连续成功完成间隔逐渐从约 17.7 秒降至 11.7 秒，随后 `movie/2053515` 被 400 拒绝。
- **下一次 movie 成功相隔约 371 秒。** 09:36:30 的失败之后，09:42:41 成功的是 `movie/2056650`，并非刚才失败的 `2053515`。这证明该端点随后可成功请求，不能当作 `2053515` 已恢复的证据。
- **重启后的失败间隔并不固定。** 以 11-01 17:58 重启后的记录计，相邻失败间隔中位数约 **9.76 分钟**，范围约 **5.30–17.74 分钟**；“每次固定 7–10 分钟”过于绝对。

完成日志是在成功响应后的节流 sleep 和落库结束时记录，因而上述间隔是可观测的**完成间隔**。371 秒还包含客户端冷却、调度等待及成功后的 sleep，不能精确等同于服务端封锁持续时间。

历史依据见[豆瓣源依赖性与脆弱性分析](豆瓣源依赖性与脆弱性分析.md)中的 rexxar movie 限流实测。本次现象与其一致，但日志不能识别服务端完整配额算法。端点独立限制是有力解释，仍不能排除并存的全局风控规则，也不能据此断言腾讯云 IP 一定比住宅 IP 更严格。

music 密集执行阶段，movie 请求受调度及类别冷却影响，不能用“该时段 movie 失败少”单独证明端点之间完全独立；最后一次 music 完成前 4 秒，16:13:22 已有一条 movie 400。失败跨昼夜出现，但当前数据不足以证明严格的时段无关性。

### 6.2 完成耗时应按有效吞吐估算

| 观察窗口 | movie 成功 | movie 400 | 有效成功速率 | 每条成功平均墙钟耗时 | 1983 条按此速率推算 |
|---|---:|---:|---:|---:|---:|
| 11-01 17:58:05 → 11-02 09:52:19 | 654 | 91 | 41.12 条/小时 | 87.54 秒 | 约 48.2 小时 |
| 11-02 00:00 → 09:52:19 | 336 | 57 | 34.04 条/小时 | 105.77 秒 | 约 58.3 小时 |

这些估算包含实际冷却和调度开销。恢复排队后若沿用相近条件，**48–58 小时**比原先的 16–30 小时更有日志依据；仍只是速率外推，不是完成承诺。新任务、重启、限流变化及未完成条目的重试都可能改变结果。

### 6.3 是否应该降低 400 频率

本次日志能确认可重试的限流拒绝，**不能证明现有吞吐已经贴近服务端配额上限，也不能证明维持吞吐时完全无法减少 400**。

把 movie 请求间隔下限提高到 45–60 秒，可以作为待验证的低频实验。该假设可能减少冷却空转、改善整体完成时间，但尚未实测，不能宣称能消除限流。现有 `SYNC_SUBJECT_MIN_INTERVAL_SECS` 是三类共用下限；若只调整 movie，需要另行设计类别参数，直接调高共用值会同时减慢 book/music。

若以后实验，应分别记录每小时成功数、每百次尝试的 400 数、失败条目等待重试的时长、总完成耗时，以及终态错误和降级量，并控制服务重启及其他抓取流量。优先比较实际完成效率，不能只看成功阶段的短间隔。

减少 400 的收益包括节省无效请求、减少冷却等待和改善可观测性，并非只有“运维观感”。对本次已完成的 4408 条缓存，没有发现限流造成的数据质量降级。

## 7. 中断行为与恢复条件

`jobs/clear` 按指定状态删除 job；它不是持久暂停开关，且不能撤销已发出的单个请求。11-02 09:52:06 清空后，09:52:19 仍写入最后一个在途结果，符合 [clear_jobs](../../backend/src/server/subject.rs) 的实现。

清空后的精确缺口是 **1983 条 movie**。访问日志只保存了清空请求成功和响应长度，没有保存响应体中的删除数量，因此本报告不把 1983 当作已核实的实际删除行数；该操作还可能删除正在执行、后来完成的那一行。

| 后续触发 | 是否能重建这批缺口 |
|---|---|
| 当前 `wenjun30` 每日订阅，计划 11-02 16:39:05 | **不能覆盖当前这 1983 条**；其已有记录全部完成，缺口属于另一用户 |
| 仅更新 book/music 的 RSS | 不能；RSS 只对本次触及的用户及类别入队 |
| 涉及缺口用户的 movie 维度同步完成 | 可以；按该用户和 movie 类别执行缺失条目差集入队 |
| 全库 `subjects/backfill` | 可以；遍历 records 中的用户/类别组合补回缺失 job |
| 关闭 `SYNC_SUBJECT_ENRICH` 并让新配置生效 | 停止 worker 的后续富集处理；这与删除当前队列是不同控制方式 |

全量同步入口见 [service.rs](../../backend/src/server/service.rs) 的 `full_sync`，实际富集入队发生在 [worker.rs](../../backend/src/server/worker.rs) 的维度完成分支；`service.rs` 中 RSS 的 `enqueue_missing_subjects` 调用仅覆盖 `by_dim` 触及的类别。二者不可混为“订阅直接对全库补队列”。

本次仅记录可选恢复路径，没有执行恢复、开关调整或订阅修改。

## 8. 运维经验与后续建议

1. **用三组指标判断任务状态。** 同时看成功覆盖率、排队重试数与终态失败/降级数。`error=0` 不能替代“全部完成”，队列清空后尤其如此。
2. **恢复必须按条目关联。** 匹配同一 `(category, subject_id)` 的失败和后续成功；端点下一条请求成功不能代表前一个失败条目成功。
3. **清空前保存快照。** 留存队列状态、失败条目键、attempts、next_run_ms、订阅覆盖范围和时间窗口；清空后只看当前 job 表会失去未完成工作的历史状态。
4. **区分删除队列和持久暂停。** 前者取消当前排队，后续适用的同步仍可重建；后者需使用配置控制。决定是否续跑前，先确认哪些用户实际启用了订阅。
5. **关注失败条目的等待公平性。** 当前失败 job 更新 `updated_ms` 后可能排到尚未尝试的旧 job 后面。后续若调整调度，应衡量重试等待时长，同时保留类别冷却，不能通过强制重排绕过冷却来追求即时恢复。
6. **后台应表达“等待重试”。** 当前列表先排 running，再排 queued，同一组按 `updated_ms DESC` 展示，最近失败的 queued 行容易位于列表前部；可考虑区分暂时失败、重试中、终态失败，并展示下次执行时间。前台排序与 worker 的取任务顺序并不相同。
7. **限速优化以整体吞吐为依据。** 重试机制避免了立即终态失败，但频繁 400 仍有真实时间成本；45–60 秒的 movie 间隔只作为实验候选，不作为未经验证的生产配置。

以上均为评估与经验归档，未实施 UI 或调度改动。

## 9. 后续复核方法

日志导出应固定时区和截止时间；归档时只保留分析所需字段，避免把完整访问日志中的身份信息或请求参数纳入项目：

```bash
ssh txy 'TZ=Asia/Shanghai journalctl -u weimo-douban \
  --since "2026-10-30 00:00:00" --until "2026-11-02 09:55:00" \
  --no-pager -o json' > /tmp/txy-enrichment-journal.jsonl
```

解析 `MESSAGE` 时兼容字符串与 UTF-8 字节数组；以 `__REALTIME_TIMESTAMP` 排序，提取“条目富集失败”和“条目元信息富集完成”。对每个失败条目查找时间更晚的同键成功，再与数据库核对。不要仅汇总 `attempt`，或把任意下一条成功当作重试成功。

SQLite 使用只读连接；以下查询分别核验当前缺口、订阅归属和 subjects/job 差异：

```sql
-- 当前未富集的条目及其用户是否启用订阅。
SELECT r.uid, r.category, COUNT(DISTINCT r.subject_id) AS missing,
       COALESCE(sub.enabled, 0) AS subscription_enabled
FROM records r
LEFT JOIN subjects s
  ON s.category = r.category AND s.subject_id = r.subject_id
LEFT JOIN subscriptions sub ON sub.uid = r.uid
WHERE s.subject_id IS NULL
GROUP BY r.uid, r.category;

-- 每个订阅当前实际覆盖的富集缺口。
SELECT sub.uid, sub.enabled, sub.next_full_ms,
       COUNT(DISTINCT CASE WHEN s.subject_id IS NULL
         THEN r.category || '/' || r.subject_id END) AS missing
FROM subscriptions sub
LEFT JOIN records r ON r.uid = sub.uid
LEFT JOIN subjects s
  ON s.category = r.category AND s.subject_id = r.subject_id
GROUP BY sub.uid;

-- 已有缓存但没有 job 行的条目，不应混入“未完成”统计。
SELECT s.category, s.subject_id, s.source, s.fetched_ms
FROM subjects s
LEFT JOIN subject_jobs j
  ON j.category = s.category AND j.subject_id = s.subject_id
WHERE j.subject_id IS NULL;
```

这些查询反映执行时的状态；若未来重新入队或有新增标记，结果会变化，应以本报告的时间边界及附带审计摘要保留本次结论。

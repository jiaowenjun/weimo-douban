# 富集任务可靠性与调度

> 2026-11-02 实施。依据：[txy 富集执行报告](../research/2026-11-02-txy富集任务执行报告与经验总结.md)。本次改造不自动重建历史上被清空的生产队列，也不自动启用 45–60 秒的限速实验。

## 1. 执行流程

1. 单 worker 优先处理收藏维度；富集领取任务时检查总开关、全局/类别暂停、全局最小间隔、类别冷却、类别间隔、单条退避和中心缓存租约。
2. 在 `BEGIN IMMEDIATE` 事务内领取 job，产生唯一 `run_token`，写入独立的执行记录。暂停、清空和领取因此有明确顺序。
3. 普通任务已有缓存时直接完成，不请求上游、不消耗请求间隔。强制刷新可以重抓缓存，但仍遵守暂停和类别冷却。
4. 请求前恢复持久化间隔，并预留下一次请求截止时间。请求返回后立即在同一事务中写 subjects、推进匹配 `run_token` 的 job、完成执行记录、保存下一次请求时间。
5. worker 依据最早可执行时间唤醒。movie 的类别间隔不再通过长 sleep 阻塞其他类别；共享最小请求间隔仍在 worker 中生效。

同类别普通任务按“最多连续两条到期重试，再给首次任务一次机会”选择；没有首次任务时重试可以继续。每组内部保留显式刷新优先，并按首次重试时间或创建时间处理较老任务。优先级不改变可执行时间，不使用 `priority=0` 绕过限流。

异常退出会留下 `started` 记录。服务器在启动 worker 前将这些记录标记为 `interrupted`，将残留 running job 恢复到 queued；保留冷却和退避。`interrupted` 代表执行结果未知，不伪装成已确认的失败或成功。

## 2. 持久化数据

| 表/字段 | 用途 |
|---|---|
| `subject_jobs.retry_since_ms` | 保留本轮首次失败时间，成功或终态时清除；旧库采用原 updated_ms 作为可得的近似起点 |
| `subject_jobs.run_token` | 区分旧在途请求与同键重新排队的任务，避免旧结果错误完成新 job |
| `subject_runtime` | `*` 行保存全局暂停/最小间隔，三类别行保存暂停、间隔、冷却截止时间、调度轮转及连续封锁状态 |
| `subject_attempts` | 每次执行的开始、结束、尝试序号、HTTP 状态、错误、结果与是否重试恢复；独立于 job 生命周期 |
| `subject_operations` | 暂停、恢复、清空、快照恢复、回填、刷新、重排的审计摘要 |
| `subject_job_snapshots` | 清空时保存完整队列状态，与实际删除在同一事务内提交 |

迁移使用幂等建表和加列，不改写历史 subjects。新统计从新执行记录产生时开始，不自动推断或导入旧 journal 的结果。历史与快照不随 job 清理删除；初版不自动过期，运维需关注数据库大小，未来若增加保留策略，应先保留累计聚合量。

## 3. 暂停、清空与恢复

**暂停**是持久化执行策略。全局或类别暂停覆盖之后新增的普通任务和强制刷新任务；允许新任务入队。恢复不重置 attempts，也不跳过未结束的冷却。总配置 `SYNC_SUBJECT_ENRICH=false` 优先于运行时恢复操作。

**清空**保留原接口语义，同时增加事务快照与审计。响应返回实际删除数、等待重试数、在途数、类别分布和快照 ID。确认框中的预览可能随 worker 推进变化，以事务提交后的响应为准。

已领取的请求允许结束。成功结果仍可写入 subjects，但只有相同 `run_token` 的 job 才能被完成；不存在的 job 不会被重新创建，同键新 job 不会被覆盖。

**恢复快照**仅插入缺失的 job，不覆盖现有队列。普通任务已有缓存时跳过；强制刷新若已有清空之后的新结果也跳过。仍在执行的条目暂不恢复，响应提示在途数，快照保留再次恢复机会。完全处理后标记快照已恢复，重复调用不会重复排队。恢复 running 快照时转为 queued，不复用旧执行 token。

## 4. 管理 API

所有接口沿用管理 API 的鉴权及限流。

| 方法与路径（相对 `/api/v1`） | 行为 |
|---|---|
| `GET /subjects/jobs/overview` | 类别执行状态、历史统计、近一小时吞吐、用户×类别覆盖缺口、最近 30 条操作 |
| `GET /subjects/jobs/history?category=movie&subject_id=123&page=1&page_size=10` | 独立执行历史；类别/条目过滤可省略，页大小上限 100 |
| `POST /subjects/jobs/control` | `{"category":"all","paused":true}`；category 支持 all/movie/book/music，返回在途数 |
| `POST /subjects/jobs/clear` | 原 states/category 参数不变，额外返回 `operation_id/retrying/in_flight/by_category` |
| `POST /subjects/jobs/restore/{operation_id}` | 恢复清空快照，返回 `restored/in_flight`；已经恢复时返回 `already_restored` |
| `POST /subjects/jobs/requeue` | 原 scope/category 不变，新增持久化操作记录，仍遵守暂停/冷却 |
| `POST /subjects/backfill` | 显式全库缺口回填，事务内入队并审计；不自动修改订阅或暂停状态 |

overview 区分：

- 当前队列：首次等待、执行中、等待重试、已到期重试、最长重试等待、到期调度延迟、终态错误。
- 历史事件：成功、重试后成功、HTTP 400、降级、未确认结果的中断。缓存命中不计入近一小时请求量。
- 覆盖结果：权威元信息、intro 缓存、缺失、已排队、没有 job 的缺口、订阅及下一次全量同步时间。总览覆盖率按用户收藏计，跨用户相同条目可能分别计入；实际抓取仍全局去重。

等待重试总时长包含冷却及暂停；到期延迟只在未暂停且已满足退避、类别和中心缓存等待条件时计算。累计降级次数与当前 intro 缓存数是不同口径。

## 5. 限速配置与实验

原默认值保留：通用下限 3 秒、成功乘 0.9、Blocked 乘 3、上限 90 秒；类别冷却默认 300 秒加不足 30 秒抖动。

| 环境变量 | 默认 | 用途 |
|---|---|---|
| `SYNC_SUBJECT_MOVIE_MIN_INTERVAL_SECS` | 未设置，继承通用值 | movie 独立下限；候选 45 或 60 秒不影响 book/music |
| `SYNC_SUBJECT_MOVIE_INITIAL_INTERVAL_SECS` | 未设置，使用 movie 下限 | 没有有效历史时的起始间隔 |
| `SYNC_SUBJECT_PACING_TTL_SECS` | 86400 | 历史间隔有效期；超期使用初始值，未结束的冷却仍保留 |
| `SYNC_SUBJECT_ADAPTIVE_COOLDOWN` | false | 实验开关，连续失败探测按 1/2/4/8/16 倍增加冷却，通常封顶 1800 秒；若原配置更大则保留原配置 |

类别下限和初始间隔会约束在 0.5–90 秒；恢复历史值时再次按当前配置约束。自适应冷却只针对连续 `Blocked` 请求，期间成功或其他类型失败会重置封锁计数；“成功几条后再失败”不会继续按旧封锁次数递增。

可控离线实验：

```bash
python3 scripts/enrichment_pacing_sim.py --subjects 1983 --seed 20261102
```

[本次实验结果](../research/evidence/2026-11-02-enrichment-pacing-simulation.json)使用两种明确假设的令牌桶配额，不连接豆瓣，也不拟合实际配额。较宽松模型中 45 秒下限减少冷却并提高吞吐；严格模型中 45/60 秒仍有封锁，完成时间没有改善。它验证“收益依赖配额语义”，不能作为生产耗时预测。

线上实验步骤：先记录基线、保持任务范围与冷却策略稳定，仅调整 movie 下限；比较成功数/小时、400/请求数、重试等待时长、总完成时长及降级量，再决定是否保留。不要同时改变下限与自适应冷却。需要部署新版本、确认具体任务范围后才能形成线上实测结论。

## 6. 验证与运维

新增回归覆盖：旧库重复迁移、暂停跨重启及新强制任务、冷却覆盖新任务、重试轮转、快照恢复保留状态、清空与在途完成竞态、及时落库、事务回滚、间隔 TTL、连续封锁实验、缺口归属和 API 鉴权。

中心缓存命中仍沿用原有独立通道，不计入豆瓣请求量；完成普通 job 时同步清除重试状态。验证也覆盖批量重排的全部/单类别过滤，以及 404 终态在冷却结束后仍不自动重试。

本地验证已通过后端回归、管理端 TypeScript 与生产构建、离线实验结果复现及 diff 检查。管理页使用独立数据库和虚构条目验证了全局/类别暂停、清空 5 条任务（其中 2 条等待重试）、恢复快照、执行历史查询及未订阅用户缺口展示；没有向豆瓣发送测试请求。

本次仅完成本地实现和验证，尚未部署到 txy，也没有执行线上限流对照实验。

部署前按[部署手册](../../ops/txy部署手册.md)备份 SQLite。升级后首先检查 overview 的暂停和缺口状态；历史统计为空是正常的新起点。需要继续此次 1983 条历史缺口时，使用明确的回填操作；不要仅凭 error 页签为空判断任务完成。
